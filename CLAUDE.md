# All In Ascent — notes for Claude

## Local and online play must stay in sync

- All game rules live in `engine/` (`state.js`, `engine.js`, `helpers.js`). Local hot-seat play, online play (PartyServer on Cloudflare Workers: `party/game.js`, wired up by `party/server.js` and `wrangler.jsonc`) and the bots (`sim/`) all run this one engine.
- `game.js` holds the GAME DATA (source of truth for characters, routes, gear) and the UI only. Never add a rule, formula or legality check to `game.js` or `online-mode.js`: ask the engine (`AscentEngine.getLegalActions`, `findLegalAction`, `explainIllegalAction`, helpers) and present the events `applyAction` emits.
- The browser loads the engine as `engine/engine.browser.js`, generated by `engine/build-browser.js` (it must keep working from `file://`, so no ES module imports in the browser scripts). After changing `engine/*.js` or the GAME DATA section of `game.js`, run `npm run data:build` and commit the regenerated `engine/data.js` and `engine/engine.browser.js`.
- If something the UI needs is missing from the engine (a value, an event field, a reason string), add it to the engine rather than computing it in the UI.
- Local and online play have feature parity, not just rule parity: a screen or feature added for one mode ships for both in the same change. Example: the post-game summary — `engine/stats.js` `summarizeGame(state)` computes every statistic from the event log, and game.js `showGameSummary` renders it for local play and for online play (online-mode.js passes the usernames).
- Telemetry: finished games become match records built by the engine (`engine/match-record.js`), and every dashboard number comes from `engine/match-report.js`; `dashboard.js` only lays them out. New things to measure go into those modules (with tests in `engine/test-match-record.js`), not into the page.
- Card availability comes from `getLegalActions` (game.js `isLegalNow`); the text on an unavailable card comes from `illegalActionReason` (a `code` plus details), which game.js `uiBlocker` only words. Never re-check costs, gear or occupancy in the UI to decide or explain.
- Project Mode (feature flag `projectMode`, `flags.js`): player-made climbers, routes and gear live in `engine/content.js` — the element catalog (`CONDITIONS` / `EFFECTS`), the compilers and the rule evaluator (`ruleEffects` / `effectSum` / `hasEffect`). A new rule element is added to the catalog there and hooked into the helper that owns the matching printed rule (never into game.js or project.js); it gets assertions in `engine/test-content.js`. The builder (`project.js`) and the review queue (`review.js`) only render what the engine compiles and words (`describeRule`). A game with workshop content is created with `createGame({ content })` and must still replay from seed + characters + content (`replayInEngine`).

## Before committing

Run `npm test` (lint with zero warnings, generated-file check, engine unit tests, party tests including the Worker test in workerd, Playwright end-to-end tests) and fix every failure. Add tests with every change:
- rule changes: assertions in `engine/test-*.js`;
- UI or flow changes: a Playwright spec in `tests/e2e/`. Local-play specs must keep checking that a UI-played game replays identically through the engine (`replayInEngine` in `tests/e2e/support.js`).

Rule changes that alter outcomes get a note in `engine/version.js`.
